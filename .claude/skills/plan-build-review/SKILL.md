# 规划 → 实施 → 审查

一次开发拆成三种角色：**主代理**（当前会话）只负责规划、分发、审查和验收；**实施子代理**（general-purpose）负责写代码；**审查不通过就回到同一个子代理修复**。

核心原则：子代理说“做完了”只是线索，不是证据。主代理一律以磁盘上的 diff 和实际命令输出为准。

## 何时使用

- 改动跨 2 个以上文件，或同时涉及 `backend/` 和 `frontend/`
- 任务能拆成若干互不阻塞的子任务
- 用户明确要求主代理规划、子代理实施、主代理审查

**不适用**：单文件小修、纯问答、只需读代码的调研（直接用 Explore 或 Plan 子代理）。

## 角色边界（硬性）

**主代理**
- 读代码、写计划、切分任务、指定文件所有权
- 派发子代理、汇总结果、亲自验收
- 用 `git diff` 和实际命令输出做审查
- **不写实现代码**。唯一例外：修复不超过约 10 行且只涉及一处时可以直接改，但必须在最终汇报中明确说明改了哪里、为什么没交回子代理。

**实施子代理**
- 只在任务卡划定的可写文件内修改
- 自己运行任务卡要求的验证命令，如实报告输出
- 不 commit、不 push、不改 `.env`、不装依赖、不扩大范围
- 需要改所有权之外的文件、或需要产品决策时，停下来报告，不擅自决定

## 阶段 0：主代理摸清现状

规划前自己读，不要一上来就派子代理探索：

1. `git status`、`git log --oneline -5` 确认工作区和当前分支
2. 定位相关模块入口、现有测试、项目约定（分层、命名、错误处理、i18n、API 调用方式）
3. 确认验证命令真实存在（`package.json` scripts、测试目录、CI 配置）

需要大范围搜索时，派只读的 **Explore** 子代理，一次只问一个维度；需要方案权衡时用 **Plan** 子代理。它们的产出只作为规划输入，不作为实施结果。

## 阶段 1：主代理写计划

计划必须包含：

- **目标与验收标准**：写成可观察、可机器验证的表述，不写“优化一下”
- **子任务拆分**：每个子任务一张任务卡
- **依赖关系**：哪些可并行、哪些必须串行
- **文件所有权矩阵**：同一文件在任一时刻只能归一个子任务
- **风险点与回滚方式**

拆分原则：

- 按文件/模块切，**不按步骤切**，避免两个子代理同时改同一文件
- 每个子任务都能独立验证（有自己的测试，或至少能通过类型检查/导入）
- 前后端接口变更放在同一个子任务，或先改后端并保证向后兼容

## 阶段 2：派发实施

- 无依赖的子任务在**同一条消息里并行派发**多个 Agent 调用，`subagent_type: general-purpose`
- 有依赖的串行；下游必须拿到上游的实际产物（diff 或确定的接口签名），而不是“已完成”三个字
- 每张任务卡必须**完整自包含**——子代理看不到主代理的上下文
- 使用 Agent 工具即可；**不要用 Workflow 工具**，除非用户明确要求多代理编排
- 子代理默认后台运行，完成时会收到通知。等待期间不要重复派发同一任务，也不要在结果回来前替它下结论；`run_in_background: false` 只在下一步确实无事可做、必须立刻拿结果时才用

**任务卡模板：**

```
目标：<一句话>
背景：<为什么改；相关文件路径>
可写文件：<穷举路径或 glob>；除此之外一律只读
约束：<必须沿用的现有模式、兼容性要求、禁止事项>
验收标准：
- [ ] <可观察结果 1>
- [ ] <可观察结果 2>
必须运行的验证：<具体命令 + 工作目录>
报告格式：
- 改了哪些文件、为什么
- 每条验收标准是否满足
- 命令输出原文（失败就贴失败内容）
- 未完成项、偏离任务卡之处、风险
```

任务卡写不好的典型症状是“实现 X 功能”配一句“测试一下”，子代理只能自由发挥，审查时也无法判定对错。

## 阶段 3：主代理审查

子代理的报告用户看不到，主代理必须自己核验：

1. `git status` + `git diff`（必要时先看 `git diff --stat`），逐个文件读实际改动
2. 检查越界：任务卡外的文件是否被改、有没有顺带重构或格式化噪声
3. 逐条对照验收标准，能跑的就跑
4. **亲自运行验证命令**，至少覆盖被改模块和相关回归
5. 按下方清单检查常见缺陷

审查结论只有三种：**通过 / 需修复 / 需返工**。发现问题时给出 `文件:行号` + 具体问题 + 期望行为，不要只说“再检查一下”。

## 阶段 4：修复回路

- 优先用 `SendMessage` 把问题发回**原来那个子代理**（它保有上下文），而不是重新派一个
- 一次列完同一子任务的所有问题，减少往返轮次
- 修复后主代理重新跑验证；通过前不得进入汇报
- 同一问题连续两轮没修好，换策略：缩小任务范围、主代理自己接手（并说明）、或向用户说明卡点

## 阶段 5：汇报

- 改了什么、为什么
- 实际跑了哪些验证、结果如何；**哪些测试被跳过、为什么**
- 偏离计划或任务卡的决定
- 剩余风险与后续建议

## 审查清单

**正确性**
- [ ] 边界条件、空值、并发与流式场景（本项目重点：SSE 流式链路、异步模型、会话状态恢复、请求结果回放）
- [ ] 错误路径有处理，失败信息能定位问题
- [ ] 没有把阻塞调用塞进异步路径

**范围与一致性**
- [ ] 只改了该改的，无顺手重构、无格式化噪声
- [ ] 沿用现有分层：后端 `app/api` → `app/services` → `app/models` / `app/schemas`；前端 `views` / `stores` / `api` / `composables`
- [ ] 命名、日志、异常风格与周边代码一致

**本项目专项**
- [ ] 前端文案改动同时更新 `frontend/src/i18n/messages/` 的中英文键
- [ ] API 变更保持向后兼容，或同步修改了前端调用方
- [ ] 涉及权限或用户隔离的接口有鉴权校验
- [ ] 数据库结构变更考虑已有数据（迁移脚本或兼容读取）
- [ ] 未提交 `.env`、密钥、日志、`_testdata/`、构建产物

**验证**
- [ ] 后端：`cd backend && python -m unittest discover -s tests -t . -v`
- [ ] 前端：`cd frontend && npm run typecheck && npm test && npm run build`
- [ ] 新增或修改的行为有对应测试，或说明了为什么不需要
- [ ] 跳过的用例（例如未设置 `TEST_DATABASE_URL` 的真实数据库测试）在汇报中明确标注

## 本项目的验证命令

| 范围 | 命令 | 说明 |
| --- | --- | --- |
| 后端全部测试 | `cd backend && python -m unittest discover -s tests -t . -v` | 与 `.github/workflows/checks.yml` 一致 |
| 后端真实数据库测试 | 设置 `TEST_DATABASE_URL`（库名必须以 `_test` 结尾）后同上 | 未设置时相关用例跳过，不能算通过 |
| 前端类型检查 | `cd frontend && npm run typecheck` | `vue-tsc --noEmit` |
| 前端测试 | `cd frontend && npm test` | 基于 `node --experimental-strip-types` |
| 前端构建 | `cd frontend && npm run build` | 含类型检查与包体积/依赖拆分断言 |

两个容易踩的坑：

- `frontend/package.json` 的 `test` 脚本**逐条列出测试文件**。新增 `frontend/tests/*.test.ts` 时必须同步加入该脚本，否则不会被执行。
- `npm run build` 不只是打包，还断言单个 JS 包不超过 500 kB、应用入口不超过 200 kB、所有业务页面保持动态入口（懒加载），并校验入口与登录页不引入 `markdown-it`、`highlight.js`、Element Plus 表格/上传组件和 `@noble/hashes`。涉及路由、视图或新增依赖时必须跑，同步 `import` 一个视图就会让它失败。

手动验证可参考 `start-backend.bat` / `start-frontend.bat` 与 README 的启动说明。

## 反模式

- 主代理自己把代码写完，子代理只挂名
- 子代理说“测试通过”，主代理没看到输出就采信
- 两个子代理同时改同一个文件
- 任务卡不写可写文件和验收标准
- 审查只看 diff 不看原文件上下文
- 发现问题的第一反应是重开一个子代理，丢掉原有上下文
- 修复循环里只修表面症状，不回看验收标准
